# payments

**MVP** — owns `PaymentIntent`, `PaymentAttempt`, `PaymentSplit`, `Refund`, `ProviderLedgerEntry`, `Wallet`, `WalletTransaction` (see `prisma/schema/payments.prisma`), per File 11 Part 03.

Pay-at-clinic ledger mechanics (Phase 5, unchanged) are documented at each use-case's own doc comment (`CapturePayAtClinicPaymentUseCase`, `ProcessCancellationRefundUseCase`).

Added 2026-09-05 (Part 50, Payments Phase 9 — DEC-001 resolved as **Paymob**, per File 10 Part 10's recommendation): online gateway payments and the internal MedSuper wallet.

- **Gateway abstraction**: `PaymentGatewayPort` (`application/ports/`) / `PaymobPaymentGatewayAdapter` (`infrastructure/`) — the only class that talks to Paymob's Accept API (auth token → order → payment key → card iframe / Fawry reference / mobile-wallet redirect). No direct Vodafone Cash/Etisalat Cash/Orange Cash integrations — Paymob's own aggregator handles all three telecom wallets behind one `initiateMobileWalletPayment` call. `PAYMOB_*` env vars are all optional (DEC-001 credentials aren't provisioned yet) — every gateway call throws a clear `PAYMENT_GATEWAY_NOT_CONFIGURED` error rather than pretending to succeed until they are.
- **Online capture** (`CARD`/`FAWRY`/`MOBILE_WALLET`): `InitiateOnlinePaymentUseCase` (creates the `PaymentIntent`+`PaymentAttempt`, calls the gateway) and `CaptureOnlinePaymentUseCase` (webhook-driven `CREATED→CAPTURED`, writes an `EARNING` ledger entry — not pay-at-clinic's `COMMISSION_DEDUCTION`, since the platform now holds the money via the gateway). `MarkOnlinePaymentFailedUseCase`/`HandleLatePaymentAfterExpiryUseCase`/`CancelOnlinePaymentIntentUseCase`/`FindPaymentByGatewayReferenceUseCase` round out the state machine — see `scheduling-appointments/README.md` for how the webhook actually reaches these (that module hosts the webhook controller to avoid a circular import).
- **Internal wallet** (`Wallet`/`WalletTransaction`): prepaid only — no negative balance, no credit/debt, no "settle balance." `POST /v1/wallet/top-up` (card-only) → `InitiateWalletTopUpUseCase` → `ProcessWalletTopUpUseCase` credits the balance only from a verified capture webhook, never on request. `CaptureInternalWalletPaymentUseCase` is `ConfirmAppointmentUseCase`'s `INTERNAL_WALLET` branch — debits via `WalletRepository.debit`'s single conditional `UPDATE ... WHERE balance >= amount` (the only correct way to prevent a concurrent overdraft; never "read balance, check in app code, write balance"). A wallet-funded appointment's cancellation refund credits the wallet back through a new `WalletTransaction` (type `REFUND`) — see `ProcessCancellationRefundUseCase`.
- **Known limitation**: an actual gateway refund call for a cancelled `CARD`/`FAWRY`/`MOBILE_WALLET`-paid appointment is NOT implemented — no such business rule exists in File 10/11 yet, so `ProcessCancellationRefundUseCase` only records the `Refund` row for those methods (identical to pre-existing pay-at-clinic behavior), same as before this phase. Only `INTERNAL_WALLET` refunds actually move money (into the wallet), because that's the one case a business rule for exists.
- Webhook authenticity is HMAC-SHA512-verified per Paymob's documented field order (`PaymobPaymentGatewayAdapter.verifyWebhookSignature` — re-check this exact field list against Paymob's current docs before go-live); `webhook_events` (File 11's existing table) provides delivery idempotency via a `WebhookEventRepository` in `shared/core/webhooks/` (new — genuinely cross-cutting, same pattern as `PolicyConfigReader`).
